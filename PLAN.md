## Decisions
- D1: Scope? -> Weight and nutrition charts plus the FTP / W-kg charts, i.e. every chart currently pushed to Datawrapper. No sleep, HRV, readiness or training-load charts (user: "sleep is not what i'm after… this should be for all the recent charts replacing in datawrapper").
- D2: Cronometer? -> Retired ("crono is dead and retired"). Nutrition comes only from the `nutrition_daily` view.
- D3: Peloton/Strava split? -> Not needed now (user: "this doesn't matter right now").
- D4: Approvals? -> None. Plan, launch and self-verify without asking (user: "pass off to orchestrator without my approval… don't ask me for anymore approvals"). Matches standing feedback: the agent verifies its own work.
- D5: Look and feel? -> "polished and engaging", in the style of Apple Health / Oura / Cronometer, and of MacroFactor and Happy Scale for weight (smoothed trend over faint weigh-in dots, change-over-range summary, goal-date projection). The Datawrapper versions "looked bad".
- D6: Stack (from the user's brief) -> Node backend with a dedicated read-only Postgres role and pre-aggregated JSON only; static single-page HTML/JS with Apache ECharts and no build step; Docker + docker-compose; token in the URL (`/d/<token>`) validated server-side, rotatable via env; frame-ancestors limited to Notion; light/dark via prefers-color-scheme plus `?theme=light|dark`; `?demo=1` / env demo mode with fake data; README; screenshots at desktop and 390 px with visual fixes before done.
- D7: Day-counting rule -> a nutrition day counts when `calories > 0` and `logged_complete IS DISTINCT FROM false`. This is the rule already used by the weekly review (`notion-reporter/src/utils/nutritionWeek.mjs:47`). The Datawrapper builder's stricter `logged_complete = true` rule is dropped.
- D8: Colors -> calories green, protein blue. This keeps PR #6's choice; the other categories get their own accents (see T5).
- D10: (Q4) Light accents vs the 3:1 rule? -> A: keep the 3:1 rule and darken three light accents, same hues: calories `#1E9E3C` (3.49), carbs `#B86E00` (3.99), over `#E06100` (3.57). Dark accents unchanged. Answered by the planner under D4 (no approvals); planner-verified ratios against `#FFFFFF`.
- D9 (auto, T3): aggregate.test.mjs "no effective goals row leaves goal null" looks up 2026-09-20 with rangeDays 30, outside the range 2026-09-27..2026-10-26 -> spec writer fixes the test (use rangeDays 90 or a day inside the range before the earliest goals row); the implementation is unchanged [source: Default policy, spec test that looks wrong; no user-visible behavior, data, security or cost impact]
## Assumptions
- A1: Node over Python, because `health-mcp` and `notion-reporter` already establish Node 22 + `pg` + `node --test` on the Pi, so there is one runtime and one test harness.
- A2: The plan pace is 0.75 kg/week, the user's chosen rate (`notion-reporter/src/anthropic/analyzeHealth.mjs:127`). The server reads it from env `PLAN_KG_PER_WEEK`, default `0.75`.
- A3: Both the full dashboard (`/d/<token>`) and single-panel embeds (`/d/<token>?view=<name>`) are needed. The user currently places separate Datawrapper charts in Notion, and a Notion embed has one fixed height, so single panels at 460 px or less are the main embed on phones.
- A4: ECharts is served from `node_modules/echarts/dist/echarts.min.js` under `/assets/vendor/`, not from a CDN. Assets then come from `'self'` only and no third party sees the page, so no token leaks through Referer. It is still free/OSS and needs no build step.
- A5: Postgres and cloudflared run on the Pi host, so the container uses `network_mode: host` and binds `127.0.0.1:8878`. The ingress rule is `charts.michaelfigari.com → http://localhost:8878`. The compose project name is `health-dashboard`; it does not edit any other compose stack.
- A6: Datawrapper jobs are removed in this PR (T12/T13). Rollback is `git revert`. The published Datawrapper charts stay on datawrapper.de with their last data until the user deletes them.
- A7: "Today" and day boundaries use America/Los_Angeles, the same as `nutrition_daily` and `build_nutrition_charts.py:31-34`.
- A8: Weight trend = exponentially smoothed daily series (alpha 0.1, the Hacker's Diet / MacroFactor-style 10% smoothing). Weigh-in gaps are linearly interpolated per calendar day, and the trend restarts after any gap over 30 days. It is deterministic and testable.
- A9: Test PG restart: `"/c/Program Files/PostgreSQL/18/bin/pg_ctl.exe" -D "$LOCALAPPDATA/hdh-test-pg/data" -l "$LOCALAPPDATA/hdh-test-pg/server.log" -o "-p 5433 -c listen_addresses=localhost" -w start >/dev/null 2>&1 </dev/null`.
- A10: Visual QA drives the locally installed Microsoft Edge through `playwright-core` (`channel: 'msedge'`), so no browser download is needed. It runs locally only, not in CI.
## Default policy
- If ambiguous, follow the existing pattern in `health-mcp/config.mjs:1-60` (env parsing and validation that throws) and `health-mcp/db.mjs:1-18` (pools), and log the choice in the task's Notes.
- Files: ESM `.mjs`. Server code lives in `dashboard/src/`, browser code in `dashboard/public/`, tests in `dashboard/test/{unit,integration,visual}/`. Never create a directory named `db/`, `lib/`, `build/` or `dist/` under `dashboard/`: `db/` is a protected-path pattern and the others are gitignored at the repo root.
- Dependencies (exact versions, no caret): `express@4.21.2`, `pg@8.13.1`, `echarts@5.6.0`; devDependency `playwright-core@1.49.1`. Add nothing else.
- Privacy: SQL names columns explicitly (no `SELECT *`) and never selects `meals_json`, `notes`, `title`, food item names or any `*_raw` table. Logs carry method, path with the token replaced by `[redacted]`, status and ms. Never log Authorization headers, query parameters, query results, response bodies or row values. Error logs carry `err.code` and `err.message` only.
- Browser modules export pure option builders (`(data, tokens, opts) => echartsOption`) that never touch `window`/`document` at import time, so node unit tests can import them. DOM wiring lives in `public/js/app.mjs` only.
- Chart work: if the `dataviz` skill is available, load it before writing chart code or choosing colors.
- Report needs-decision only for: user-visible behavior not covered above, data loss, security, cost, or a spec test that looks wrong.
